**Lazy sync can be a FULL DAY stale — force a Send/Receive, don't just passively re-scan (learned 2026-07-10):** on the 07-10 scheduled run the first COM read showed newest = **07-09 04:17** (an entire day of mail missing), and a passive re-scan alone would not have fixed it. The reliable remedy: `ns = outlook.GetNamespace("MAPI"); sync = ns.SyncObjects; for i in range(1, sync.Count+1): sync.Item(i).Start()` (group 1 is "All Accounts"), then `pythoncom.PumpWaitingMessages()` + `time.sleep(5)` in a poll loop re-reading `Items.GetFirst()` until the newest item's date is today (it caught up on the **first** poll here). Always force this at the start of a scheduled run before trusting the window.

**Lazy sync can be 2+ DAYS stale over a weekend, AND one script's forced sync may only PARTIALLY catch up — verify newest==today and re-run in a fresh process if not (learned 2026-07-13):** the 07-13 (Mon) run's first `scan_inbox.py` pass — *with* the forced Send/Receive above — only reached newest = **07-10 16:19** (the whole weekend still missing, ~2 days short). It looked stable across 4 polls (a false "caught up"). A **second, fresh Python process** doing the same forced sync then pulled current to **07-13 04:34** (count 4,988 → 5,198), and a third full re-scan confirmed it stable. So: the first forced-sync pass can stall mid-catchup; **always confirm the newest item's date == the real today, and if not, run the sync again (a fresh process helped) before trusting coverage.** Count growing during polling = sync still working = not yet trustworthy.

**`/auto` sync gaps are NON-monotonic — newest==today does NOT mean the window is complete; a MIDDLE time-range can still be missing (learned 2026-07-27):** on the 07-27 (Mon) run the first COM pass showed `/auto` newest = 07-27 04:03 (the Monday 02:00–04:00 fund cluster synced fine) and "both current to today" on poll 0 — but the entire **Sunday-evening 07-26 17:00–20:30 CLO chain** (CLO Loan Pricing/Surveillance, Loan index, Intex Transaction Loader SUCCESS, intex db checker OK, Listing/Galileo, Nightly risk check) was **absent** from that first dump. **COM datetimes are LOCAL wall-clock mislabelled as GMT — strip tzinfo, NEVER call `.astimezone()` (corrected 2026-08-05, supersedes the 07-09 note):** `ReceivedTime`/`SentOn` come back as `pywintypes.datetime(..., tzinfo=TimeZoneInfo('GMT Standard Time', True))`, but the value they carry is already **local EDT wall-clock**, not UTC. So `.astimezone()` subtracts 4 hours and reports every message 4 hours early. Verified two independent ways on 2026-08-05: (1) the Sent Items entry for `Daily RESI/CLO Summary - 2026-08-04` has raw `2026-08-04 08:23:21`, matching `outputs/daily-resi-clo-summary-20260804.md`'s 08:23:05 mtime exactly, while `.astimezone()` rendered it `04:23`; (2) an inbound mail whose raw stamp was `09:34:40` arrived while `datetime.now()` read `09:40` — a UTC value would have been impossible. **How to apply:** use `rt.replace(tzinfo=None)` and compare against naive `datetime.now()`/naive cutoffs. Consequence to remember: the **07-09 through 08-04 summaries report all email times 4 hours early** — do not treat their timestamps as ground truth when reconstructing history.
