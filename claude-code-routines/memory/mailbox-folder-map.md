**COM store-index gotcha (learned 2026-07-09):** `ns.Stores.Item(1)` is **NOT stably the primary mailbox** — across two runs minutes apart it was `hzeng@LIBREMAX.com` once and `Online Archive - hzeng@libremax.com` (empty Inbox → 0 items, a false "empty inbox") the next. **Always select the primary store by DisplayName** (`== "hzeng@libremax.com"`, excluding the "Online Archive"/"Public Folders" stores), never by index. Also: `ReceivedTime` via COM is genuinely tz-aware **UTC** — use `rt.astimezone()` to get EDT (don't hand-subtract, and don't treat it as naive-local). And the primary Inbox **syncs lazily**: a first scan at 08:12 showed newest = prior-day 15:22 with 4,474 items; a re-scan minutes later showed the current-morning batch (newest 07-09 04:13, 4,523 items). **Re-scan / confirm the newest item is same-day before trusting coverage.** Archive retention is a rolling 12 months (this run: Jenkins Automation frozen at 2025-07-08).

**Lazy sync can be a FULL DAY stale — force a Send/Receive, don't just passively re-scan (learned 2026-07-10):** on the 07-10 scheduled run the first COM read showed newest = **07-09 04:17** (an entire day of mail missing), and a passive re-scan alone would not have fixed it. The reliable remedy: `ns = outlook.GetNamespace("MAPI"); sync = ns.SyncObjects; for i in range(1, sync.Count+1): sync.Item(i).Start()` (group 1 is "All Accounts"), then `pythoncom.PumpWaitingMessages()` + `time.sleep(5)` in a poll loop re-reading `Items.GetFirst()` until the newest item's date is today (it caught up on the **first** poll here). Always force this at the start of a scheduled run before trusting the window.

**Lazy sync can be 2+ DAYS stale over a weekend, AND one script's forced sync may only PARTIALLY catch up — verify newest==today and re-run in a fresh process if not (learned 2026-07-13):** the 07-13 (Mon) run's first `scan_inbox.py` pass — *with* the forced Send/Receive above — only reached newest = **07-10 16:19** (the whole weekend still missing, ~2 days short). It looked stable across 4 polls (a false "caught up"). A **second, fresh Python process** doing the same forced sync then pulled current to **07-13 04:34** (count 4,988 → 5,198), and a third full re-scan confirmed it stable. So: the first forced-sync pass can stall mid-catchup; **always confirm the newest item's date == the real today, and if not, run the sync again (a fresh process helped) before trusting coverage.** Count growing during polling = sync still working = not yet trustworthy.

**`/auto` sync gaps are NON-monotonic — newest==today does NOT mean the window is complete; a MIDDLE time-range can still be missing (learned 2026-07-27):** on the 07-27 (Mon) run the first COM pass showed `/auto` newest = 07-27 04:03 (the Monday 02:00–04:00 fund cluster synced fine) and "both current to today" on poll 0 — but the entire **Sunday-evening 07-26 17:00–20:30 CLO chain** (CLO Loan Pricing/Surveillance, Loan index, Intex Transaction Loader SUCCESS, intex db checker OK, Listing/Galileo, Nightly risk check) was **absent** from that first dump. A second forced Send/Receive backfilled that middle range (count 13,268 → 13,745). Had I trusted the first pass I would have wrongly reported "no in-scope CLO activity — weekend cadence." **Takeaway: `newest.date()==today` is necessary but NOT sufficient — Exchange cached-mode fills newest-first and backfills the middle later. ALWAYS run a second forced sync + a full re-dump of the window and confirm the item COUNT is stable before trusting the in-scope inventory.** Note the CLO evening chain runs on the business date's evening (~17:00–20:30), so a Monday-morning run covers the PRIOR business date (Fri 20260724 over that weekend); Monday's own CLO chain runs Monday evening, after the ~08:10 scan.

**Subfolder vs top-level Inbox sync lag goes BOTH directions — force-sync-poll `/auto` until newest==today, don't trust its first read (learned 2026-07-16, corrected 2026-07-17):** on 07-16 the top-level primary `Inbox` stayed wedged at the prior-evening item (07-15 20:10) across 3 forced-sync passes / ~7 min while `Inbox/auto` was already current to 07-16 04:07 on the first read — so "read `/auto` directly, don't block on the parent" held. **But 07-17 was the REVERSE:** the first pass showed top-level `Inbox` current to 07-17 04:11 while `Inbox/auto` was STALE at 07-16 04:30 (missing the entire overnight business-date-20260716 batch). A single extra forced Send/Receive + pump/sleep poll caught `/auto` up to 07-17 04:08 (count 4960→5056) on the second poll. **Takeaway: never trust `/auto`'s first-read newest — after the initial sync, verify `/auto` newest.date()==today and, if not, loop `SyncObjects.Item(i).Start()` + `PumpWaitingMessages()`/sleep re-reading `/auto` newest until it reaches today (usually 1 extra poll).** The `resync_auto.py`/`dump_auto.py` scratchpad pattern from the 07-17 run does exactly this. Still scan the top-level Inbox too (sparse human mail + GitHub CI); whichever of the two lags, the forced-sync poll fixes it.
