# AGENTS.md — LMQR Workspace

## Learned User Preferences

- Required model columns should fail loudly; use defensive name guards only for genuinely optional fields or supported aliases such as `OriginalRating` versus `original_rating`.
- Keep CLO features, caps/floors, filters, weights, and hyperparameters in one config source; put reusable helpers in utility files, keep training drivers thin, and preserve interactive RStudio execution for research R scripts.
- Capped or floored features use a `c_` prefix while raw columns retain their original names; config/report keys must use the actual capped column names or plots can be skipped silently.
- Research and test runs must write to separate sandbox paths and dev tables, never overwriting production JSON, production stats tables, or prod jobs. Before release, regenerate the standard artifacts and run the JSON replay/tieout.
- Diagnostic metrics and plots must use the same observation weights as the fitted model; unweighted fits require unweighted diagnostics.
- When extending a production CLO report, preserve its existing formatting and add the requested columns or summary pages instead of replacing it with a new report layout.
- Default to the smallest change that works; expect pushback on extra columns, seed data, validation flags, compatibility shims (such as an inverse transform for a target no release model uses), and intermediate `GAM-Candidate`-style serving configs when the intent is to replace the production entry directly; justify any new guardrail with the concrete failure it prevents. Delete configs for models that were never released instead of keeping them, and never commit scratch or test files alongside a production fix.
- The user opens their own PRs and often prefers to run long or production commands himself, so hand over the exact command instead of executing it. Do feature work in a separate worktree rather than switching the main checkout, and publish with `git push -u origin HEAD`, since a worktree branch created from `origin/master` inherits it as upstream and branch protection rejects a push to `master`.
- A definition change is never local: apply it across every product config that shares it (CAS, STACR, MIR, NQM, LP/Jumbo) and their pseudo variants, keep pseudo and core on one shared query instead of divergent copies, and match the R reference implementation in RCode exactly when one exists. Shared warehouse-derived fields such as `servicer_map` belong in that shared unload SQL as a table join, not as name lists in each product `*_config.py`.
- Model configs in `clo_model/spread_model/config.py` and `pygam_configs.py` hold raw literal values: no importing constants from another config module, no dict-spreading another config, no module-level constants standing in for values; pin cross-file agreement with a test instead. Each sub-model versions itself through `sub_model_name`/`sub_model_version` in its own JSON metadata, so the outer `ModelName`/`ModelVersion` (`GAM`/`v3.0`) is not bumped for a sub-model release. New CLO sub-models are released as a `--versions` entry in `clo_dm_based_model_train.py` (Jenkins `quant-CLO-spread-model-train`), not as a one-off proc.

## Learned Workspace Facts

- In R, variable-driven `data.table` selection requires `df[, ..cols]` or `df[, cols, with = FALSE]`; `else` must be on the same line as the preceding `}`.
- For pooled AAA+AA+A GAMs, normalize features with non-overlapping rating distributions by frozen rating-level means (`x / rating_mean`). Use `Rating`, not `f_OrigRating`, because production prediction fields must match `CLOSpreadModelBond`. EUR A-AAA reporting keeps these senior-fit conventions and the shared `research_howard` helpers, including `c_OfferSize` over `1k-4mm`, `c_AAAFactor` over `0.95-1.0`, `weight_mode`, and weighted diagnostics.
- The BBB research filter `MVOC <= 1.03` must never be copied to AAA/AA/A; senior MVOCs are much higher and that filter drops every row. OFFER is the ListingType reference level across GAM and LGBM models.
- `clo_model/procs/clo_dm_based_model_train.py` owns registry-based production training for `v1`, `v2`, `v2r`, and `delev` (Jenkins `quant-CLO-spread-model-train`, `--asofdate YYYYMMDD --versions v2 v2r delev`); training artifacts land in `S:/QR/Risk/CLOCache/{dm_based_model_v2,delev_model}/YYYY-MM-DD/` and only the `*.json` files are copied to `core/<root>/YYYY-MM-DD/` plus the root when that date is the newest. `v2r` writes EUR-senior artifacts into the V2 roots, including `S:/QR/Risk/CLOCache/core/dm_based_model_v2/`; `Broad-Prod` now resolves to `GAM_MODEL_CONFIG_V3`, so EUR senior DM-based JSONs are active rather than falling through to the MVOC curve. Driver gotchas: `--cutoff-start` defaults to `2024-01-01` and overrides every config's `cutoff_start` through `replace()` in `build_configs_for_date`; `copy_jsons_to_production` sweeps every `*.json` in the dated training folder, so debug JSONs must sit in a subfolder; `get_latest_production_date` globs every `????-??-??` folder with no filename filter, so two models must never share a production root or one pushes the other into backfill mode and its root pointer goes stale; `_parse_model_keys` uppercases `--models CCY/RATING` tokens. Classic production GAM training is a separate path: `half_life=30` at the call site in `spread_model/gam.py`, fit with `time_weight` only, without the listing-type multipliers LGBM research uses.
- Production results live in `Libremax_rd.dbo.clo_spread_model_result`. Select the release with outer `ModelName`/`ModelVersion` (`Broad-Prod` is currently `GAM`/`v3.0`), filter the workflow with `Purpose` and `Scenario`, and deduplicate by latest `RunDateTime`, then `RunID`, per security/date. `Purpose` identifies run usage, not the submodel; use `ModelOutputJson` fields such as `sub_model_name` and `sub_model_version` for submodel identity, and expect some EUR-only rows only under `Galileo-*` purposes. Delevered models are price-based and `RiskSpreadModel` already converts model price to risk spread for the outer result, so evaluation must not apply a second DM-to-price conversion. `GAM_MODEL_CONFIG_V3` serves USD and EUR delevered bonds from separate JSONs: `price_based_model_curve_filenames` entries are joined to `price_based_model_base_dir` (`core/delev_model`) with as-of-date resolution (USD, `direct_price`), while `price_based_model_curve_path` entries are static paths (EUR pooled `core/price_based_model_terms.json`, `exp_upper`), so swapping one currency's entry cannot move the other's prices; `zero_prediction_features=["f_ListingType"]` makes served values mid-style, so any comparison against Broad-Prod must zero the listing term too. Fixed-rate CLO bonds never reach the DM model's training set because `CpnSpread` is parsed from the floating `Formula` and training drops NaN `CpnSpread`/`DM_Maturity`; their Intex Z-spread is `FundStudio.dbo.riskdb_hist.e_spread` for marks (`disc_margin` is the DM, there is no `z_spread`/`zv_spread` column, OAS purposes overwrite `e_spread`, TMRS/SWIB read the same table on `GalileoClient`) and `Libremax.dbo.DealerColorRiskResults.RiskSpread` for color quotes (the same `e_spread` renamed by `colordb/run_color_risk_results.py`, with `DM` = `disc_margin`); `clo_model_scenario_pricing.DM` is not a Z-spread.
- Export `scam`/`gam` models with the term classes in `clo_model/model/gam/terms.py` and EUR-senior `mgcv::bam` with `clo_model/model/gam/export_bam_json.R`; production replays JSON through `GAMReplayModel.from_partial_dependence_json()` using PCHIP, with no R dependency at prediction time. The V2R Python config exports features, caps, and hyperparameters to JSON for `clo_dm_based_model_train_r.R`, and Python-to-R calls require an `Rscript` preflight, timeout, captured stderr, and atomic temporary-file rename. `WrapperGAM.get_partial_dependence_data` writes every `by=Rating` curve on one grid spanning the pooled feature range (`wrapper.py:359-380`), so PCHIP flat extrapolation reproduces a training clip only for plain splines; per-rating caps (a BB curve is stored out to the BBB cap) must be re-applied at serving, and `PRICE_BASED_CAP_FLOOR_RULES` EUR wildcards (BBB 1.20 / BB 1.10 / B 1.05) match the live pooled EUR model's training caps in `lmunittests/clo_model/research/price_based_model.py` only by coincidence, so a model trained with different clips must carry its own bounds. A price-based JSON must declare `transform_upper` in its metadata or `curve.py` silently inverts with 101.2.
- A CoreLogic LP `factor_date` of month M reports month M-1 activity, while a DV01/Figure platform tape stamped `as_of_date` month-end M reports month M activity, so Figure-sourced HELOC legitimately runs one activity month ahead of NonQM/Jumbo/CRT; settle any "is this column mislabelled?" question by comparing paid-in-full month and modal `loan_interest_paid_through_date` within each tape rather than reasoning from `agencydata/config/resi_date_offsets.py`. Deal-level DV01 accounts then lag the `Figure Platform` account by about a month because `lmdv01/dv01_update_platf.py` inner-joins FIGRE deals to their deal-level account (all except `FIGRE 2023-HE1A2` and `GRADE*`), so GRADE deals and HELOC pseudo pools pick up a new tape first; join the two feeds on `line_of_credit_id` from `mortgage_static_data`, since `dv01_id` is account-scoped and `loan_id_reported` carries a `FIGURE-` prefix only on the platform side, and run the queries through `lmdv01.dv01_utils.execute_dv01_big_query`. DV01 static tables are live snapshots that get restated (`orig_ltv`, `original_upb`, `loan_balance_orig`), so `dv01_update_platf.py --force_unload` on a historical month rewrites `orig_*` fields with today's values; without it, months before a deal's first existing flat file are skipped with only an INFO log (`--factor_dates` narrows the months), and a join fix is validated on loan-id set and current-UPB totals, not byte diff.
- Model-result rows under the same key carry two payload shapes: nightly ECA rows hold vectors only, monthly rows also hold `ALL.Transition`. Transition consumers must pass `require_transitions=True` to `getLatestCollatScen` in `lmsimvectors/model_run_result_db_manager.py` or the newest row can be an ECA payload and the read fails with a `KeyError`; vector consumers legitimately need the unfiltered path. SIM2 model versions are duplicated in `lmsimvectors/config/sim_config_common.py` (read by tracking, `vectorlib`, `crt_deal_manager`) and `sim_config_sim2.py` (read by `lm_sim_pub_main._get_model_version`, the label stamped on `ResiTransitionTracking` and vector rows); the label never selects the model file, since `get_model_path` resolves `SIM2_MODEL_PATHS`/`SIM2_HELOC_MODEL_PATHS` by deal type and uses the version only to pick GRADE/FIGURE, so a model adoption must change the paths and both version tables together or production rows carry the old label and tracking finds zero rows. Model JSONs live in `C:\Git\LMSimData`, the C++ engine in `C:\Git\LMSim`. A tracking job dying with `Expected N results ... only M became visible within 120s` is a Ray OOM on the 7.45 GB nodes (see `\\libremax-nas\QR_sanbox\QR\logs\sim\*_sim2_raysubmit_*.log`): `_await_ray_jobs` still calls `get_results()` after the job FAILED, and `_load_sim2_asset_for_ray` (`sim2_arrow_bundle.py`) and `_process_chunk` (`lmray/dataset.py`) declare no `memory=` reservation, unlike `_persist_result_batch` in `lmray/__main__.py`, so running products one at a time does not prevent it.
- Raw disclosure tables sit months apart, so no job may assume one shared "current factor month": measured on 2026-08-13, `fnma.fnm_crt` was at 202605, `fnma.fnm_sf` at 202509, both `fhlmc` dyn tables at 202606, and `trst.usbank_ll`, `lps.lp_dyn` and the Figure platform at 202607. Drive every query off its own table's `max(date_column)` instead of a current-and-previous-month window, and treat a month as usable only once its row count reaches 90% of the prior month's (the rule already codified in `agencydata/wh_nqm_pseudo_sample.py`), because partial early data lands mid-month. `fnma.fnm_sf` lags about eleven months by design (a slow feed, not a dead table) and has no REO timeline, so it cannot train an REO/FCLS model. CRT/product "SF" is Fannie `fnma.fnm_sf`; `fhlmc.fhl_sfll_dyn` / `fhl_sfll_stat` is the separate Freddie Mac loan-level tape (Webb/Hill), not a missing CRT source.
- `executeSQL(db="padb", ...)` takes the pyodbc branch in `lmdata/lmdb.py` because `WH_DB = "padb"` (around line 852), not the SQLAlchemy `else` path. Autocommit is off and the connection is closed without committing, so DDL/DML silently rolls back unless the SQL ends with `commit;`. Each call still gets a fresh connection, so staging cannot be `TEMPORARY`; use a real table with a unique suffix and drop it in a `finally`. `executeSQLRedshiftDF` is the `redshift_connector` path, so do not cite one as the other. Redshift qualifies `UPDATE` target columns by table name alone (`servicer_map.col`, never `lib.servicer_map.col`) and rejects row-constructor `IN` lists such as `WHERE (a, b) IN ((...),(...))`. `lmdb` is the Azure PostgreSQL reached through pg8000 (`postgresql+pg8000://`), not Redshift; `get_metadata_context` builds a fresh engine and disposes it on exit, so `Table(..., autoload_with=engine)` inside a per-row loop (as `getForwardModelRunFromDBJson` does) pays a connect, TLS handshake and schema reflection per lookup and is what times out under parallel report processes.
- Run repo commands from the checkout root with `uv run --frozen python` (`--no-dev --group full` for production-style scripts, `--with pytest` for tests because pytest is not in the locked groups); never the `pyprod` conda env, and a bare `python` resolves to base miniconda without the dependencies. The repo is not installed into `.venv` (`pyproject.toml` has `py-modules = []`), so `import clo_model` resolves from the cwd or `PYTHONPATH`: a `$env:PYTHONPATH="C:\Git\LMQR"` left in the shell, or a script parked in `$env:TEMP`, silently imports the main checkout while you think you are testing a worktree, so clear it or point it at the worktree, which keeps its own `.venv`. PowerShell `$arr[-1] = x` assigns the last element, so a lookup helper returning -1 on a miss silently overwrites the end of a file; guard the return before indexing. `Read`/`StrReplace` can also act on a stale cached snapshot, so when an edit tool insists text is missing that you know exists, confirm the true line count through the shell before writing.
- Figure publishes no servicer field: `loan_servicer_primary`, `loan_servicer_master`, `loan_seller` and `loan_origination_channel` are entirely blank on `lib.mortgage_static_data_figure_platform`, and `loan_originator` is the only populated identity column (about 17% blank, roughly 22 distinct values). Mapping Figure on `loan_originator` is intentional, not a defect; the core-file `loan_servicer_primary as servicer_name` alias is a later config change, not mapping-table work. Any Figure-sourced servicer variable really means originator. LPS current-servicer for `lib.servicer_map` is `lps.lp_stat.servicer` (`st.servicer`), not the `lps.lp_svcr.servicer_curr` snapshot. LPS text columns such as `servicer`, `pool_id` and `loan_id` are blank-padded `CHAR`, so always `upper(trim(...))` before comparing or grouping. Resi flatfiles take `servicer_map` from a SQL join to `lib.servicer_map`; map every raw string (no volume cutoff), send blank/NA to Other, and key `data_source` by warehouse table name. Include Freddie SF servicers in that table even though CRT unloads still read only Fannie SF. The shared resi `property_type` CASE maps `asset_type`/`prop_type = 'Other'` to `MH` in `dv01_config.py`, `dv01_config_platf.py`, `dv01_pseudo_config.py`, `intex_config.py` and `wh_scrt_config.py`, labelling unknown property type as manufactured housing; changing it is one definition change across all five.
